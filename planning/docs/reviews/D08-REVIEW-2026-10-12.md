## Findings, ordered for action

### 1. Blocker: restore a compilable application and test suite

- `ui/TalaApp.kt:6` and `ui/interview/InterviewWorkspaceScreen.kt:6` import `ActivityContracts`, while their picker code uses `ActivityResultContracts`.
- `TalaApp.kt:40,58` and `InterviewWorkspaceViewModel.kt:14,48` reference `EnumeratorProfileStore`; no declaration exists in the inspected source tree. The profile ViewModel instead requires the concrete `DataStoreEnumeratorProfileStore`.
- `data/DataStoreEnumeratorProfileStore.kt:14–15` assigns the preferences delegate with `=` instead of declaring a delegated property with `by`. Line 26 calls `map` on `DataStore` instead of its data flow. Line 38 assigns a nullable picture path to a string preference instead of removing the preference when absent.
- `HouseholdRepository.kt:167–174` uses the unresolved, unqualified `HOUSEHOLD_PHOTO` constant in the implementation.
- `ui/profile/EnumeratorProfileViewModel.kt:60` supplies null to the non-null `message` property. Lines 65, 81 and 94 access `message` on `WriteResult` without narrowing to `Failed`.
- `src/test/.../domain/form/QuestionnaireSectionsTest.kt:1` contains only the literal `null`. The `ShellViewModelTest` repository fixture also lacks the new required photo write methods.

The online build confirmed the main-source compilation defects listed above. The test-source defects were found by inspection; test compilation was not reached. Action: align the profile-store contract and implementation, correct the picker imports and DataStore access, qualify the attachment constant, handle both write outcomes explicitly, and repair the test sources. Require a fresh APK build and unit-test pass before claiming functional completion.

### 2. High: photo operations can discard unsaved household answers

`InterviewWorkspaceViewModel.kt:141–158` cancels the pending autosave, performs the photo operation, and reloads the section on success without first persisting its dirty answers. For example, edit a household field and immediately remove its existing photo before the 500 ms debounce expires: the reload restores the older saved answers. A pending failed save can be discarded the same way. This is a source-traced failure path, not a device reproduction in this review.

Action: serialize photo changes with draft saving, stop if the draft save fails, and preserve edits made during asynchronous work. Add regression coverage for removal during the debounce and after a failed draft save.

### 3. High: profile pictures report success before their reference is durable

`EnumeratorProfileViewModel.kt:70–97` changes only UI state when choosing/removing a photo, while displaying `Saved`. It never calls the profile store in those operations. `PhotoStore.kt:61` deletes the previous profile image immediately. Replacing/removing an existing picture and leaving without pressing the separate Save profile button leaves the persisted path pointing at a deleted file. A first picture's path is lost after process restart unless that separate save succeeds.

The name/barangay setters also retain a prior Saved phase after further editing.

Action: persist the new profile reference before reporting success or deleting the old image. On failure, retain the old durable profile and image; clean up the new staged file. Clear saved acknowledgements when edits change the draft.

### 4. High: household photo replacement/removal lacks safe cleanup

`PhotoStore.kt:32–51` writes a new household file and replaces its database row, but never removes the prior household file after successful replacement. Removal deletes the file before committing removal of its database reference: a database failure leaves a dangling attachment. File writes and deletions also lack complete failure handling; write exceptions can escape the coroutine, and failed deletes can still be reported as success.

Action: stage the new file, commit the reference change, then clean up the old file. On unsuccessful persistence, preserve the old reference/file and remove the staged file. Removal should preserve recoverability if the reference update fails. Cover file-write, database-write and cleanup failures, including interrupted replacement.

### 5. High: image handling does not match the agreed specification

The technical requirements specify **5 MiB input**, JPEG/PNG/WebP, a maximum **1600 px longest side**, and a normalized target of **at most 1 MiB**. `PhotoStore.kt:30` instead caps household images at **4096 bytes (4 KiB)**; profile images have no cap. Line 74 reads the entire stream into memory before any household size check. There is no decode validation, resizing or normalization. Files get a `.jpg` suffix regardless of their actual contents.

File reads/writes are synchronous and are invoked from the ViewModels' default main-thread coroutine context. Both photo slots render status text/buttons rather than an actual image preview (`InterviewWorkspaceScreen.kt:94` and `TalaApp.kt:469`).

Action: implement one bounded image-processing path for both owners, perform media IO/processing off the UI thread, enforce the documented limits, reject invalid images, preserve correct encoding metadata, and render previews of the saved copies.

### 6. High: registration has competing identity sources

`HouseholdRepository.saveDraftSection` derives household/member display names from structured answers (`HouseholdRepository.kt:117–123`). However, the separate household editor's `replace` method (`:214`) updates only the household row, and `saveMember` (`:182`) changes only the member display name. Their structured answers remain unchanged.

Example: save First Name `Ana`, Last Name `Reyes` in the questionnaire, then rename the member `Ana Cruz` in the roster. The roster and questionnaire now disagree after successful saves; subsequently saving the demographics section can restore `Ana Reyes` to the roster. The same problem applies to the household name and address. This conflicts with PR-07's explicit consistency requirement.

Action: route both editors through one authoritative identity model or update the structured answers and summary row together. Preserve legacy unsplit names until users provide structured components. Verify edits through both entry points and after restart.

### 7. High: isolate device-test photo storage before running the new suite

`RegistrationDeviceTest.kt:36,52–53` uses the installed application's target context, then recursively deletes its entire `files/attachments` and `files/profile` folders in teardown. Its separate test database does not isolate those folders from existing app records.

Action: inject dedicated temporary media directories and a separate profile store/test application, with cleanup limited to files owned by that test. Do not run this teardown against a phone containing saved app photos.

### 8. Acceptance evidence is insufficient for completion

There are useful foundations: `RegistryUiState` calculates total/male/female/unrecorded counts from active household members; the Room query selects demographics sex answers; the new JVM count test includes an unrecorded member. However, no fresh passing result establishes those paths in the current source tree.

The new device test closes/reopens a database and checks a two-member Male/Female fixture. It does not exercise the full UI, actual picker, process restart with profile DataStore, or unrecorded-sex counts after restart. Its image fixtures are repeated byte value `7`, not valid images. Its replacement assertion at line 116 requires deleting the old file, which the current implementation does not do; that assertion is expected to fail once the build reaches this test, not reported here as an executed failure.

Profile attribution is also seeded only when an empty setup section is opened (`InterviewWorkspaceViewModel.kt:69`), not durably captured when a household is created. Creating a household under profile A, changing to B, then first opening setup can attribute that earlier household to B. Decide and implement the PR-01 creation-time behavior explicitly.

Action: add meaningful regression and acceptance coverage for the issues above. Preserve the existing count derivation but test actual ViewModel/UI emissions after edit, removal, archive/restore and restart.
